# Stakeholder Communication

## 목적
주어진 문제와 데이터, 요구사항을 근거로 웹 서비스 구현에 영향을 미치는 미확정 사항을 담당자에게 질문하고, 답변을 추적하여 개발 계획에 반영한다. 질문 작성과 답변 반영은 동일한 Skill에서 처리한다.

## 1. 질문 생성
1. 문제 설명, 요구사항 문서, 데이터 파일과 스키마를 읽고 서로 대조한다. 확인하지 못한 파일 내용은 추측하지 않는다.
2. 명시된 사실, 합리적 가정, 누락된 정보, 모순, 담당자만 결정할 수 있는 정책을 구분한다.
3. 데이터의 식별자, 관계, 결측치, 중복, 단위, 갱신 주기, 개인정보 및 사용 권한을 검토한다.
4. 사용자 역할, 주요 업무 흐름, 입력/출력, 필수 기능, 예외 처리, 완료 기준, 평가 범위의 불명확한 점을 검토한다.
5. 각 의문이 실제 화면, API, 데이터 모델, 검증 방식, 구현 범위에 어떤 영향을 미치는지 분석한다.
6. 담당자에게 물어야 할 질문과 개발팀이 스스로 판단할 기술적 세부사항을 분리한다. 이미 자료에 답이 있는 질문은 제외한다.
7. 필수(답변 없이는 설계/구현 불가), 권장(구현 품질/정확도 영향), 선택(후속 개선)으로 우선순위를 정한다.
8. 담당자가 바로 답할 수 있도록 한 질문에 한 가지 결정만 담고 가능한 경우 선택지와 답변 기한을 제안한다.

## 질문 목록 출력 형식
각 질문마다 아래를 기록한다.
- 질문 ID (예: Q-001)
- 질문 및 우선순위 (필수/권장/선택)
- 질문 배경과 확인 목적
- 근거 (문제/요구사항 항목, 데이터 파일·컬럼·예시)
- 가능한 답변 선택지 (확정된 선택지가 있을 때만)
- 답변에 따라 달라지는 구현 사항
- 답변 상태 (미질문/답변 대기/답변 완료/재확인 필요)
- 미응답 시 영향과 차단 여부

담당자에게 전달할 간결한 질문 목록과 개발팀 내부용 영향 분석을 구분해서 작성한다.

## 2. 답변 수신 및 반영
1. 담당자 답변을 질문 ID에 연결하고 답변 원문, 수신 시점, 출처를 기록한다.
2. 질문과 답변의 대응 관계를 검증한다. 복수 해석이 가능하거나 일부만 답변된 경우 임의로 확정하지 않고 '재확인 필요'로 표시해 후속 질문을 만든다.
3. 답변을 확정된 요구사항/업무 규칙/데이터 해석/제약사항으로 구조화한다. 기존 요구사항과 충돌하면 충돌 내용 및 우선 적용 여부를 담당자 또는 사용자에게 확인한다.
4. 변경 영향 범위를 추적한다: 화면과 사용자 흐름, 기능 명세, 데이터 모델, API, 권한, 테스트 수용 기준, 기술 스택 및 Phase 계획.
5. 질문 ID와 변경 근거를 대화 및 현재 작업 계획에 반영한다. 별도 결정·상태 문서는 요청이 있을 때만 작성한다.
6. 기존 구현이 답변과 불일치하면 수정이 필요한 파일/기능과 재테스트 항목을 제시한다. 승인된 범위를 벗어나는 변경은 사용자 승인을 요청한다.
7. 담당자 답변은 요구사항 확인이지 다음 기능 구현에 대한 사용자 승인과 동일하지 않다. `.harness/approval-harness.md` 및 기능별 보고·승인 절차를 그대로 따른다.
8. 변경된 수용 기준을 테스트 계획에 반영하고, 구현 완료 후 보고서에 질문 ID, 반영 내용, 검증 결과, 미해결 사항을 포함한다.

## 답변 반영 결과 출력 형식
- 질문 ID / 담당자 답변 요약 / 답변 상태
- 확정된 결정과 근거
- 수정된 요구사항 및 문서
- 구현 영향 및 수정 필요 항목
- 추가 질문 또는 충돌 사항
- 사용자 승인 필요 여부 / 다음 조치

## 규칙
- 담당자 답변이나 데이터 내용을 만들어내지 않는다.
- 질문을 많이 만드는 것보다 구현을 좌우하는 핵심 질문을 우선한다.
- 미응답, 모호한 답변, 담당자 확인을 사용자 승인으로 간주하지 않는다.
- 답변으로 변경된 사항은 추적 가능하게 기록한다.
- 관련 테스트를 실제로 수행하지 않았다면 검증 완료라고 보고하지 않는다.
