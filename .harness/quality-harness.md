# Quality Harness

## 목적
각 기능과 Phase가 수용 기준을 충족하는지 실제 실행 결과로 확인한다. 빌드 성공만으로 테스트 완료라고 판단하지 않는다.

## 필수 검토 테스트 계층
1. 정적 검사: 프로젝트에 맞는 타입 검사, 린트, 빌드.
2. Unit: 함수, 입력 검증, 데이터 변환, 비즈니스 로직.
3. Integration: API, 데이터베이스, 인증 및 모듈 간 연동.
4. E2E: 핵심 사용자 시나리오의 시작부터 결과 확인까지 자동 검증.
5. 실제 브라우저 UI: 가능한 경우 브라우저를 실행해 렌더링, 클릭, 입력, 이동, 콘솔 오류, 주요 화면 크기와 반응형 레이아웃을 확인한다. Playwright 등 사용 가능.
6. 회귀·최종 검증: 수정 영향 범위와 요구사항·담당자 답변의 수용 기준을 대조한다.

## 적용 원칙
- 각 기능에서 관련된 계층을 선정해 실제 실행한다. 적용 가능한 Unit/Integration 검사를 생략하지 않는다.
- 웹 서비스의 핵심 사용자 흐름은 Phase 종료 전 E2E 및 실제 브라우저 검증을 우선적으로 수행한다. E2E 자동화와 화면·레이아웃 점검은 구분해 기록한다.
- 도구·브라우저·테스트 환경이 없다면 없는 환경을 꾸며내지 않고 실행 제약, 시도 내용, 대체 검증, 남은 위험을 기록한다.
- 테스트에 필요한 패키지 설치나 설정 변경은 프로젝트 규칙 및 승인 범위를 따른다.

## 보고와 판정
- 각 검증 계층을 PASS / FAIL / NOT RUN / NOT APPLICABLE 중 하나로 기록한다.
- PASS: 실제 실행 및 통과 증거가 있을 때만 사용한다.
- FAIL: 실행했으나 실패. 재현 방법, 원인, 영향과 수정·재실행 결과를 기록한다.
- NOT RUN: 적용 대상이지만 실행하지 못함. 사유와 위험을 기록한다.
- NOT APPLICABLE: 해당 기능에 적용되지 않음. 판단 근거를 기록한다.
- Phase 보고서에 테스트 명령, 케이스, 실행 결과, 브라우저·화면 크기(해당 시), 미해결 문제를 기록한다.
- 필수 검사가 실패하거나 핵심 검증을 실행하지 못한 경우 무조건 통과로 처리하지 말고 사용자 판단 필요 사항으로 올린다.
